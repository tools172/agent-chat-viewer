# CI/CD 与社区开发标准详解

## 一、什么是 CI/CD

### 1.1 用大白话说

想象你和一个朋友合写一本书。你写第一章，他写第二章，最后要把两章合并成一本书。如果等到全部写完再合并，你会发现两人的写法完全不同——格式不统一、内容有重叠、甚至互相矛盾。

CI/CD 就是解决这个问题的：

- **CI（持续集成）**：每写完一小节，就自动检查——格式对不对、有没有错别字、和之前的内容有没有冲突。发现问题立刻修复，而不是等到整本书写完才发现。

- **CD（持续交付/部署）**：检查通过后，自动把书排版好、生成 PDF、上传到出版社。整个过程不需要人手操作。

在软件开发中，CI/CD 就是：**每次提交代码，自动运行检查（编译、测试、格式化），全部通过后才允许合并到主分支，然后自动构建发布**。

### 1.2 为什么需要它

没有 CI/CD 时：

```
程序员A: "我改完了，你帮我看看能不能用"
程序员B: "我这周也改了很多，合并起来好痛苦..."
程序员A: "咦，你的代码在我电脑上跑不起来啊"
程序员B: "你装了那个依赖没有？"
程序员A: "什么依赖？"
——3 小时后——
"算了，先提交吧，反正大部分功能是好的"
```

有 CI/CD 时：

```
程序员A: 提交代码 → Push 到 GitHub
机器人: "正在检查... 类型检查通过 ✓  测试通过 ✓  格式正确 ✓"
程序员B: 提交代码 → Push 到 GitHub
机器人: "正在检查... 类型检查通过 ✓  测试通过 ✓  格式正确 ✓"
项目经理: "看到两个 PR 都绿了，合并！"
机器人: "正在构建... 构建成功 ✓  已发布到测试环境"
```

**核心价值：把重复的、易出错的检查工作交给机器，让人专注于创造。**

## 二、CI/CD 的组成部分

### 2.1 版本控制（Git）

一切的基础。代码历史、分支管理、协作的基石。

```
main 分支 ───●──────────●──────────●── 稳定版本，随时可以发布
              \        /          /
dev 分支  ────●──●──●──●──●──●── 日常开发
                   \
feature 分支 ───────●──●── 开发新功能
```

**关键概念**：
- **commit**：一次修改的快照，包含改动内容和说明
- **branch**：独立的工作线，互不干扰
- **merge**：把两个分支的改动合在一起
- **PR（Pull Request）**：请求把某个分支的改动合并到另一个分支

### 2.2 代码质量门禁

在代码进入主分支之前，必须通过一系列自动化检查。就像飞机起飞前的安全检查单，任何一个红灯都不能起飞。

#### 2.2.1 类型检查（Type Check）

TypeScript 项目必须有这一步。它的作用是检查代码中的类型错误。

```typescript
// ❌ 类型错误：试图把字符串传给需要数字的函数
function add(a: number, b: number) { return a + b; }
add("hello", 5);  // TypeScript 编译器会在这里报错

// ✓ 正确
add(3, 5);  // 通过
```

这个项目的类型检查命令：
```bash
pnpm lint    # 实际运行的是 tsc --noEmit，只检查不生成文件
```

#### 2.2.2 代码风格检查（Lint）

确保代码风格统一。多人协作时，如果每个人的写法都不一样，读代码会非常痛苦。

```typescript
// 写法一：单引号、有分号、两个空格缩进
const name = 'hello';
if (name) {
  console.log(name);
}

// 写法二：双引号、无分号、四个空格缩进
const name = "hello"
if (name) {
    console.log(name)
}
```

两种写法都能跑，但混在一起就很难看。ESLint 会强制所有人用同一套规则。

这个项目的 lint 命令：
```bash
pnpm lint:eslint
```

#### 2.2.3 格式化检查（Format Check）

比 Lint 更进一步——不仅检查风格，而且自动把代码格式化成标准样式。

```bash
pnpm format:check    # 检查格式是否标准（CI 里用）
pnpm format          # 自动格式化（本地开发用）
```

Lint 管"对不对"，Format 管"好不好看"。比如 Lint 会检查你有没有声明了但没用的变量；Format 会检查你的缩进是 2 个空格还是 4 个空格。

#### 2.2.4 自动化测试（Test）

这是最重要的一道门禁。测试代码验证你的功能是否正常工作。

```typescript
// 一个简单的单元测试
it('加法应该返回正确结果', () => {
  expect(add(1, 2)).toBe(3);
});
```

每次提交代码后，CI 自动跑一遍所有测试。如果某个测试突然失败了，说明你的改动破坏了现有功能——这就是"回归 Bug"。测试就是你的安全网。

这个项目的测试命令：
```bash
pnpm test    # 运行全部 256 个测试
```

### 2.3 构建验证（Build Check）

光代码没报错还不够，还要确保能真正编译成可运行的程序。特别是 Tauri 这种跨平台桌面应用，涉及的环节很多：

- 前端代码要编译成 HTML/JS/CSS（Vite 打包）
- Rust 后端要编译成二进制文件
- 两者要能正常通信

CI 里的构建步骤就是模拟一次完整的编译打包过程，确保不会出现"我电脑上能跑，但别人电脑上跑不了"的情况。

### 2.4 工作流自动化（GitHub Actions）

这是 CI/CD 的"引擎"。在 GitHub 上，它叫做 GitHub Actions。

它的工作原理很简单：**当某个事件发生时，自动执行一系列命令**。

```yaml
# 这是本项目的 CI 配置文件 .github/workflows/ci.yml
name: CI                          # 工作流名称

on:                               # 触发条件
  push:
    branches: [main]              # 当有人往 main 分支 push 代码时触发
  pull_request:
    branches: [main]              # 当有人向 main 分支发起 PR 时触发

jobs:                             # 具体要做什么
  frontend:                       # 任务1：前端检查
    runs-on: ubuntu-latest        # 在 Ubuntu 虚拟机上运行
    steps:                        # 执行步骤
      - name: Checkout            # 1. 下载代码
        uses: actions/checkout@v4
      - name: Install deps        # 2. 安装依赖
        run: pnpm install
      - name: Type check          # 3. 类型检查
        run: pnpm lint
      - name: Test                # 4. 运行测试
        run: pnpm test
```

**关键概念**：
- **event（事件）**：触发工作流的事情，比如 push 代码、创建 PR
- **job（任务）**：一组要执行的步骤
- **step（步骤）**：单个命令，比如运行测试
- **runner（运行器）**：执行任务的虚拟机，GitHub 免费提供

### 2.5 并发控制

当开发者频繁 push 代码时，会触发很多次 CI 运行。但同一个 PR 只需要最新的那次运行结果。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true  # 新的运行开始后，自动取消旧的
```

比如你 1 分钟内 push 了 3 次：
- 第 1 次 push → CI 开始运行
- 第 2 次 push → CI 取消第 1 次运行，重新开始
- 第 3 次 push → CI 取消第 2 次运行，重新开始

最终只有第 3 次的结果有效。这节省了大量计算资源。

### 2.6 依赖缓存

每次 CI 运行时都重新下载依赖会非常慢。缓存就是把下载好的依赖保存起来，下次直接复用。

```yaml
- name: Cache Rust dependencies
  uses: Swatinem/rust-cache@v2     # 第三方缓存工具
  with:
    workspaces: 'src-tauri -> target'
```

类比：你每天去公司上班，不需要每天重新装修办公室。依赖缓存就是"装修一次，每天复用"。

## 三、社区开发标准

### 3.1 分支策略

最常见的模式叫做 **GitHub Flow**：

```
main ─────●──────────●────── 始终可部署
           \        /
dev  ───────●──●──●── 日常开发集成分支
              \  \
feature/A ─────●──● 新功能分支
feature/B ────────● 另一个新功能分支
```

**规则**：
1. `main` 分支永远是可运行、可发布的稳定版本
2. 任何新功能、Bug 修复都在独立分支上开发
3. 开发完成 → 创建 PR → CI 通过 → Code Review → 合并

### 3.2 Commit 规范

每次 commit 要回答两个问题：**做了什么** 和 **为什么**。

业界最常用的是 **Conventional Commits** 规范：

```
<类型>(<范围>): <简短描述>

<详细描述（可选）>
```

类型：
- `feat`: 新功能
- `fix`: 修 Bug
- `docs`: 文档
- `refactor`: 重构（不改变功能）
- `test`: 测试
- `chore`: 杂务（构建、依赖更新等）

示例：
```
feat: 多标签页系统

新增 tabStore 管理标签页生命周期，支持：
- 打开/关闭/切换/去重/拖拽排序
- 每标签页独立过滤器
```

### 3.3 Issue 和 PR 模板

模板让问题描述更规范，减少沟通成本。

**Issue 模板**包含：
- Bug 报告：期望行为 vs 实际行为、复现步骤、环境信息
- 功能请求：想要什么功能、解决什么问题

**PR 模板**包含：
- 描述：做了什么改动
- 关联 Issue：关联哪个问题
- 检查清单：CI 是否通过、是否加了测试、是否需要截图

### 3.4 Code Review

PR 发起后，至少一个团队成员审查代码后才能合并。主要审查：

1. **正确性**：逻辑是否正确、有没有边界情况没处理
2. **可维护性**：代码是否清晰易懂、有没有重复代码
3. **安全性**：有没有注入风险、权限问题
4. **性能**：有没有明显的性能问题
5. **一致性**：是否遵循项目的代码风格

### 3.5 测试覆盖率

代码覆盖率衡量"你的测试覆盖了多少代码"。比如写了 100 行代码，测试只跑了 80 行，覆盖率就是 80%。

**重要认知**：高覆盖率 ≠ 好测试。100% 覆盖率但全是无效的测试没有意义。关键是**关键路径**要有测试。

这个项目的测试命令带了覆盖率参数：
```bash
pnpm test -- --coverage    # 运行测试并生成覆盖率报告
```

### 3.6 开源项目必备文件

| 文件 | 用途 |
|------|------|
| `README.md` | 项目介绍、安装方法、使用说明 |
| `LICENSE` | 开源许可证（别人怎么用你的代码） |
| `CONTRIBUTING.md` | 如何参与贡献（开发环境搭建、PR 流程） |
| `CODE_OF_CONDUCT.md` | 行为准则（禁止歧视、骚扰等） |
| `.github/ISSUE_TEMPLATE/` | Issue 模板 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 模板 |
| `.editorconfig` | 编辑器配置（缩进、换行等） |
| `.gitignore` | 哪些文件不纳入版本控制 |

## 四、本项目 CI/CD 现状逐项分析

### 4.1 已有的优势

**① CI 流水线完整**

前端和 Rust 后端各有独立的检查流程：

```
代码提交
  │
  ├─→ 前端检查（并行）
  │     ├─ pnpm lint（TypeScript 类型检查）
  │     ├─ pnpm lint:eslint（代码风格）
  │     ├─ pnpm test（256 个测试）
  │     └─ pnpm format:check（格式化检查）
  │
  ├─→ Rust 检查（并行）
  │     ├─ cargo fmt（格式化）
  │     ├─ cargo clippy（代码质量）
  │     └─ cargo test（Rust 测试）
  │
  └─→ 构建验证（等前面两个都通过后才执行）
        └─ pnpm tauri build（完整构建）
```

**② 并发取消 + 依赖缓存**

节省 CI 运行时间和 GitHub 免费额度。

**③ 完整的开源标配文件**

README、LICENSE、CONTRIBUTING、CODE_OF_CONDUCT、Issue/PR 模板一应俱全。

**④ 自动化测试覆盖**

256 个测试覆盖了工具函数、状态管理、UI 组件三个层面。

**⑤ 类型安全**

TypeScript + Rust，两端都有编译期类型检查。

### 4.2 可以改进的地方

以下按优先级从高到低排列：

#### 4.2.1 🔴 CI 只在 main 分支触发

```yaml
on:
  push:
    branches: [main]    # ← 只监听 main 分支
```

这意味着你在 dev 分支上 push 代码时，CI 不会自动运行。只有当你向 main 发起 PR 时才会触发检查。

**问题**：你在 dev 上开发了好几周，累计了大量改动，到 PR 时 CI 才第一次跑。如果这时候发现一堆问题，修起来很痛苦。而且你无法知道是哪次提交引入的问题。

**改进**：加上 dev 分支：

```yaml
on:
  push:
    branches: [main, dev]    # dev 分支的每次 push 也触发 CI
```

#### 4.2.2 🔴 没有 pre-commit hooks（本地提交前检查）

目前项目依赖开发者在 CI 中发现问题，但问题是：CI 在云端运行，代码已经提交上去了。理想情况是：**在 commit 之前，本地就拦下问题**。

这是通过 `husky` + `lint-staged` 实现的：

```
开发者执行 git commit
        │
        ▼
    husky 拦截
        │
        ▼
    lint-staged 只检查这次改动的文件
        │
        ├─ tsc --noEmit（类型检查）
        ├─ eslint --fix（自动修复 lint 问题）
        ├─ prettier --write（自动格式化）
        └─ vitest related（只跑相关的测试）
        │
        ├─ 全部通过 → commit 成功
        └─ 有失败 → commit 被阻止，必须先修复
```

**好处**：问题在本地就解决了，永远不会提交带错误的代码。

#### 4.2.3 🟡 测试覆盖率没有设置门槛

当前 CI 运行了 `pnpm test -- --coverage`，但没设最低覆盖率要求。即使覆盖率从 80% 降到 30%，CI 也会通过。

**改进**：在 vitest 配置中设置覆盖率门槛：

```typescript
// vitest.config.ts
test: {
  coverage: {
    thresholds: {
      lines: 70,        // 行覆盖率不低于 70%
      branches: 65,     // 分支覆盖率不低于 65%
    }
  }
}
```

这样当覆盖率低于阈值时，CI 会失败，强制开发者补充测试。

#### 4.2.4 🟡 只有 Linux 构建验证

这个项目是 Tauri 桌面应用，目标平台包括 Windows、macOS、Linux。但 CI 只在 Linux 上验证构建。有些 Bug 只在特定平台出现（比如路径分隔符 `\` vs `/`）。

**改进**：加上 Windows 和 macOS 的构建 Job（但要注意 GitHub Actions 的免费额度限制）。

#### 4.2.5 🟢 没有依赖安全审计

项目依赖的第三方包可能存在已知的安全漏洞。定期检查可以提前发现风险。

**改进**：
```yaml
- name: Security audit
  run: |
    pnpm audit        # 检查 npm 包漏洞
    cargo audit       # 检查 Rust crate 漏洞
```

#### 4.2.6 🟢 dev 分支领先 origin 太多

```
当前状态：dev 领先 origin/dev 3 个提交
```

开发过程中及时发起 PR、及时合并，可以避免长期偏离主分支导致的大量冲突。

## 五、总结

### 成熟度评估

| 维度 | 状态 | 说明 |
|------|------|------|
| 版本控制 | ✅ 成熟 | Git + 合理的分支策略 |
| CI 流水线 | ✅ 成熟 | 前端 + Rust + 构建三阶段 |
| 代码质量门禁 | ✅ 成熟 | tsc + eslint + prettier + clippy |
| 自动化测试 | ✅ 成熟 | 256 个测试，覆盖三层 |
| 缓存优化 | ✅ 成熟 | pnpm + Rust 依赖缓存 |
| 开源文件 | ✅ 成熟 | README/LICENSE/CONTRIBUTING 齐全 |
| 本地提交检查 | ❌ 缺失 | 无 pre-commit hooks |
| CI 覆盖分支 | ⚠️ 不足 | 只触发 main，dev 未覆盖 |
| 测试覆盖率门槛 | ⚠️ 不足 | 跑了统计但无阈值 |
| 多平台构建 | ⚠️ 不足 | 仅 Linux |
| 依赖安全审计 | ❌ 缺失 | 无 |
| PR 节奏 | ⚠️ 可改善 | dev 领先 origin 较多 |

### 一句话总结

**本项目已经具备专业的 CI/CD 基础设施，处于中上水平。最需要补充的是 pre-commit hooks（本地提交前检查）和 dev 分支 CI 触发——这两项改动小、收益大。**
